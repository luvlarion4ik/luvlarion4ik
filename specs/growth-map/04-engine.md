# 04. Движок

Файл `docs/assets/growth-map/gm-engine.js`. Чистые функции без DOM: всё, что ниже, должно работать и в браузере, и в Node (для тестов). Экспорт через `window.DevlarionGM.engine` в браузере и через `globalThis.DevlarionGM.engine` в тестах (скрипт загружается в `vm`-контекст, см. 06-integration.md).

```js
engine.normalizeBrief(raw, catalog)          // → Brief (дозаполненный средними)
engine.buildNow(brief, catalog)              // → Variant
engine.buildVariant(brief, catalog, level)   // level: 1 | 2 | 3 → Variant
engine.buildAll(brief, catalog)              // → { now, base, boost, auto }
engine.economy(brief, variant, catalog, ctx) // → Economy
engine.compare(brief, variants, catalog)     // → Comparison (все 4 экономики + тексты разницы)
engine.layout(variant, catalog)              // → variant с x/y у узлов
engine.contribution(brief, variant, catalog) // → [{ block, money }] вклад каждого блока
engine.parseText(text, catalog, lang)        // → { brief, detected: [поля] }
engine.migrate(doc)                          // → документ последней версии или ошибка
```

## 1. Brief (бриф)

```js
{
  name: 'Барбершоп Борода',          // строка, может быть пустой
  category: 'beauty',               // id сферы
  niche: 'barber',                  // id подкатегории или ''
  nicheCustom: '',                  // если category === 'other'
  models: ['services','booking'],
  items: ['Мужская стрижка','Борода'],
  check: 1800,                      // ₽, число или null
  cycle: 'day',                     // day | week | month | long | null
  size: 'team',                     // solo | team | mid | large
  revenueBand: 1,                   // 0..4 индекс диапазона или null
  leads: 400,                       // число или null
  repeatBand: 1,                    // 0 почти нет | 1 около трети | 2 половина и больше | null
  sources: ['src_maps','src_insta'],
  mainSource: 'src_maps',
  sourcesOther: '',
  intake: ['dm','phone'],           // phone | dm | site | table | crm
  payment: ['card'],                // cash | card | terminal | online | invoice  (cash и card — оба → pay_cash)
  pains: ['lose_leads','no_repeat'],// lose_leads | slow_reply | no_repeat | ads_cost | manual | no_numbers | overload
  wishes: ['mini','payments'],      // site | bot | mini | app | portal | crm | ai | payments | broadcast | advise
  timing: 'asap',                   // asap | soon | browsing | null
  currency: 'RUB',                  // валюта, в которой пользователь вводил деньги
  filled: { check: true, leads: true, ... } // какие поля ввёл человек, а какие подставлены
}
```

Все деньги внутри движка хранятся в рублях. Если пользователь вводил чек в другой валюте, форма переводит его в рубли по курсу из `currency.js` до вызова движка, а в `currency` сохраняет исходную валюту для отображения.

### normalizeBrief

1. Неизвестные id выбрасываются. Пустые обязательные поля: `category = 'other'`, `models = category.models`, `size = 'team'`.
2. `check ?? category.check`.
3. Поток обращений `leads`:
   - если введён — берётся он;
   - иначе если есть `revenueBand`, то `leads = revenueMid / (check × conv)`, где `revenueMid` — середина диапазона (150 000 / 650 000 / 3 000 000 / 12 000 000 / 30 000 000);
   - иначе `category.leads × sizeK`, где `sizeK = { solo: .35, team: 1, mid: 3, large: 9 }`.
   - Округление до целого, минимум 10.
4. `conv = category.conv`, `margin = category.margin`.
5. `repeat0`: `[0.08, 0.33, 0.5][repeatBand] ?? category.repeat`.
6. `leak0` по таблице 03-catalog.md, раздел 5.8.
7. `hourRate`: 600 ₽/ч для `solo`, 700 для `team`, 900 для `mid`, 1100 для `large`.
8. `hoursK` (масштаб часов) = `{ solo: .5, team: 1, mid: 2.2, large: 4 }`.
9. `filled` отмечает каждое поле, которое пришло от пользователя, а не из средних.

## 3. buildNow — «Как сейчас»

1. Узлы `traffic`: все `brief.sources` (и `src_word`, если список пуст).
2. Точка входа и обработка по таблице 03-catalog.md, раздел 5.8. Если ничего не выбрано — `ent_dm`.
3. Оплата по таблице 5.8. Если ничего — `pay_cash`.
4. Исполнение и возврат пустые.
5. Связи: каждый источник → каждая точка входа; точка входа → обработка (если есть) → оплата.
6. На каждую связь от точки входа дальше ставится маркер потерь `leak: leak0` (показывается в UI как «теряется ≈ 30% заявок»).
7. Раскладка через `layout`.

## 4. buildVariant — Фундамент, Ускорение, Автопилот

Вход: `brief`, `level` (1, 2, 3). Шаги:

1. **Кандидаты.** Все блоки с `tier ≥ 1`, у которых `tier ≤ level` и выполнены условия `when`. Если `when.wishes` пересекается с `brief.wishes`, эффективный `tier` блока на единицу меньше (но не меньше 1). Блоки с `tier: 0` (только «Как сейчас») не участвуют.
2. **Желания пользователя.** Соответствие `wishes` → блоки: `site → ent_site или ent_shop (goods)`, `bot → ent_tgbot`, `mini → ent_tgmini`, `app → ent_app`, `portal → del_portal`, `crm → proc_crm`, `ai → cap_ai`, `payments → pay_acq`, `broadcast → ret_broadcast`. Желанный блок добавляется в вариант, если его эффективный `tier ≤ level + 1`. Для `ent_app` действует отдельное правило: явное желание `app` добавляет блок с «Ускорения», независимо от формата бизнеса. В «Фундаменте» блок не добавляется.
3. **Источники.** Все текущие источники пользователя входят в каждый вариант. Новые источники добавляются из подходящих по сфере, отсортированные по `t` убыванию: level 1 — 0 новых, level 2 — 2 новых, level 3 — 4 новых. `src_insta` никогда не добавляется автоматически, только если он уже есть у пользователя.
4. **Одна точка входа на уровень, без дублей.**
   - level 1: `ent_shop` если `goods`, иначе `ent_site` если сфера из его `when`, иначе `ent_landing`. Плюс `ent_tgbot`, если модель `booking` или `digital` или в pains есть `slow_reply`.
   - level 2: всё из level 1, плюс `ent_tgmini` для `booking`/`goods`/`digital`, плюс `ent_mpcard` если `goods` и `src_mp` в источниках варианта.
   - level 3: всё из level 2, плюс `ent_app` если `size ∈ {mid, large}` или `app` в wishes, иначе `ent_pwa`. Плюс `ent_maxbot`.
5. **Правило `replaces`.** Если в варианте есть блок, который вытесняет другой, вытесняемый удаляется. Обязательные пары: `proc_crm` вытесняет `proc_table`; `cap_ai` не вытесняет `cap_form` (форма остаётся для тех, кто не хочет говорить с ботом).
6. **Размер.** Для `solo` на level 1 вместо `proc_crm` используется `proc_table` + `proc_notify`; `proc_crm` появляется с level 2.
7. **Обязательный скелет**, который добавляется, если после шагов 1–6 этапа нет:
   - `capture`: `cap_booking` для `booking`, иначе `cap_form`;
   - `process`: `proc_notify`;
   - `pay`: `pay_link`;
   - `deliver` (level ≥ 2): `del_remind` для `booking`, `del_access` для `digital`, `del_status` иначе;
   - `retain` (level ≥ 1): `ret_review`.
   - `insight`: `ins_metrika`.
8. **Ограничение размера.** level 1: 8–13 узлов; level 2: 14–21; level 3: 20–30. Если больше максимума, удаляются кандидаты с наименьшим вкладом (раздел 6) среди блоков, не пришедших из брифа и не из скелета. Если меньше минимума — добавляются кандидаты следующего уровня с наибольшим вкладом, пока не наберётся минимум (это нормально: «Фундамент» маленького бизнеса может взять один блок из «Ускорения»).
9. **Монотонность.** Каждый следующий вариант содержит все блоки предыдущего, кроме вытесненных по `replaces`. Тест проверяет это.
10. **Связи** по правилам 03-catalog.md, раздел 7.
11. **Раскладка** через `layout`.

Детерминированность: при одинаковом брифе результат одинаковый (никакого `Math.random` в движке; id узлов `n1…nN` по порядку этапов и блоков в каталоге).

## 5. Экономика

Функция `economy(brief, variant, catalog, ctx)`, где `ctx = { now: Economy }` для расчёта разницы.

### 5.1. Сбор эффектов

Для каждого узла варианта берётся `fx` блока. Множители эффекта узла:
- узел без входящих и исходящих связей (кроме `traffic` и `insight`) — × 0.5;
- повтор того же блока — × 0.3;
- блоки, которые уже были в «Как сейчас», в вариантах дают эффект полностью (они — часть схемы), но в «Как сейчас» их эффект равен нулю: это и есть базовая линия.

### 5.2. Формулы

```
T     = min( Π(1 + t_i), capT )                         // рост потока
L     = leads × T                                        // обращений в месяц
leak  = max( leak0 × Π(1 − leak_i), 0.03 )               // доля потерь
conv  = min( conv0 × Π(1 + conv_i), conv0 × 2.2, 0.85 )  // конверсия
check = check0 × min( Π(1 + check_i), 1.4 )              // средний чек
rep   = min( repeat0 + Σ repeat_i, 0.6 )                 // доля повторной выручки
first = L × (1 − leak) × conv × check                    // выручка с новых
rev   = first / (1 − rep)                                // вся выручка
hours = Σ hours_i × hoursK
profit= rev × margin + hours × hourRate                  // прибыль в месяц с учётом сэкономленного времени
```

`capT = 1.25` для level 1, `1.6` для level 2, `2.2` для level 3, `1` для «Как сейчас».

Для «Как сейчас» все Π = 1, Σ = 0, `leak = leak0`, `T = 1`.

### 5.3. Потолки правдоподобия

После расчёта:
- `growth = rev / rev_now − 1`;
- потолок `growth`: level 1 — 0.45, level 2 — 1.2, level 3 — 2.4; если превышен, `rev = rev_now × (1 + потолок)` и все производные пересчитываются от него пропорционально;
- пол: level 1 не меньше 0.12, level 2 не меньше 0.3, level 3 не меньше 0.6 (если меньше — поднимается до пола; бизнес с уже хорошей системой всё равно увидит понятную выгоду).

Это и есть «оптимизм с запасом»: цифры щедрые, но не выглядят как обман на первом созвоне.

### 5.4. Потери и упущенная выгода

```
lostLeads   = L_now × leak_now                 // заявок теряется в месяц сейчас
losingNow   = (rev_auto − rev_now) × margin    // «Теряете сейчас» на нижней панели: недополученная прибыль в месяц против Автопилота
gapToNext   = (rev_next − rev_this) × margin   // для карточек разницы
yearProfit  = (profit − profit_now) × 12
```

На вкладке «Как сейчас» показатель «Утекает» = `L_now × leak_now × conv_now × check_now × margin` (прибыль от заявок, которые сейчас теряются). Это главная цифра-крючок, она должна быть видна сразу после анализа: в «Сравнении» первая строка подсвечена красным.

### 5.5. Стоимость внедрения

1. Группировка узлов варианта по `service` (узлы с `service: null` бесплатны, их настройка входит в работу).
2. Для каждой услуги `S` уровень цены `tierBySize = { solo: 'small', team: 'small', mid: 'medium', large: 'large' }`, но для level 3 уровень поднимается на ступень (small → medium), если `size !== 'solo'`.
3. Ставка из `estimator[S][tier]` (импортируется из `content/pricing.mjs` при сборке и вкладывается в страницу как JSON, см. 06-integration.md): число → `[n, n]`, массив → `[min, max]`, `null` → услуга «по смете».
4. Цена услуги в варианте = ставка × `min(1, Σ share узлов этой услуги)`. Для ставки-массива min и max умножаются отдельно.
5. Итог = сумма по услугам, округлённая вниз до 5 000 ₽ (min) и вверх до 5 000 ₽ (max). Если хотя бы одна услуга «по смете», итог показывается «от {min}» и пометка «часть работ по смете».
6. Пакетная выгода: если в варианте ≥ 4 разных услуг, к цене применяется −10%, а в инспекторе цены пишется «с учётом пакета». Это не скидка из реферальной программы и с ней не суммируется.
7. Срок запуска в неделях: `[2, 4]` для level 1, `[4, 8]` для level 2, `[8, 16]` для level 3; +50% к обеим границам для `large`.

### 5.6. Окупаемость

```
payback = priceMid / (profit − profit_now)      // в месяцах, priceMid = (min + max) / 2
```

Если знаменатель ≤ 0 или `payback > 24` — «считаем на созвоне». Иначе округление вверх до 0.5 месяца, но не меньше 1.

### 5.7. Объект Economy

```js
{
  key: 'boost', leads: L, lostLeads, leak, conv, check, rep,
  revenue: rev, profit, hours, growth, yearProfit, losingNow,
  price: { min, max, quote: false, bundle: true }, weeks: [4, 8], payback: 3.5 | null,
  defaultsUsed: ['check','leads']      // для строки «часть цифр — средние по нише»
}
```

## 6. Вклад блоков (contribution)

Вклад узла = `profit(variant) − profit(variant без этого узла)` в рублях в месяц (leave-one-out, без потолков правдоподобия, иначе вклады обнуляются у потолка). Используется:
- в инспекторе («≈ +38 000 ₽ в месяц к выручке»: там берётся разница `rev`, не `profit`);
- для обрезки варианта (раздел 4, шаг 8);
- для блока «Рекомендуем добавить» в библиотеке (топ-5 блоков следующего уровня, которых нет на карте, по вкладу при добавлении);
- для текстов разницы.

## 7. Тексты разницы («Что вы теряете, если…»)

Три карточки в «Сравнении». Каждая: заголовок, сумма, два предложения, список из 3 блоков с самым большим вкладом в разницу.

Вклад в разницу между вариантами A и B: для каждого блока, который есть в B и нет в A, считается вклад при добавлении в A. Топ-3.

Шаблоны RU (EN агент пишет по тем же правилам):

| Карточка | Заголовок | Текст |
| --- | --- | --- |
| Сейчас → Фундамент | Оставить как есть | Каждый месяц ≈ {lostLeads} заявок уходят без ответа. Это ≈ {moneyLost} прибыли, которую вы уже заплатили рекламой и временем, но не получили. Главное, что это чинит: блоки „{top1}“, „{top2}“ и „{top3}“. |
| Фундамент → Ускорение | Остановиться на «Фундаменте» | Заявки перестанут теряться, но клиенты всё ещё будут покупать один раз. «Ускорение» добавляет ≈ {gap} в месяц, то есть {gapYear} за год: прежде всего за счёт блоков „{top1}“ и „{top2}“. |
| Ускорение → Автопилот | Не включать «Автопилот» | Блок „{top1}“ работает ночью и в выходные, когда вы не отвечаете. Разница с «Ускорением» ≈ {gap} в месяц, а освобождается ещё ≈ {hoursGap} часов вашего времени. |

Если `gap` меньше 3% от выручки «Как сейчас» (такое бывает у `solo` с маленьким потоком), третья карточка рекомендует «Ускорение» без порога по заявкам. В этой модели при фиксированном брифе обе суммы меняются пропорционально потоку, поэтому перебор не меняет процент разницы.

Названия блоков подставляются в именительном падеже, с маленькой буквы, в кавычках „…“, через слово «блоков» или «блок»: «прежде всего за счёт блоков „онлайн-запись“ и „рассылки в Telegram и по почте“», «блок „ИИ-ассистент 24/7“ работает ночью…». Шаблон третьей карточки поэтому начинается так: «Блок „{top1}“ работает ночью и в выходные…». Агент движка проверяет тестом, что все шаблоны собираются без пустых подстановок для каждой сферы.

## 8. Локальный разбор текста (parseText)

Вход: свободный текст до 2000 символов. Выход: частичный `brief` и список `detected`.

1. Нормализация: нижний регистр, `ё → е`, неразрывные пробелы и тонкие пробелы в обычные.
2. **Сфера и ниша:** для каждой подкатегории считается число совпавших `keywords` (поиск подстроки по корню). Берётся максимум; при равенстве — та, что раньше в каталоге. Ноль совпадений — сфера не определена.
3. **Модели:** словари: «запис», «приём», «сеанс» → booking; «товар», «магазин», «доставк», «склад» → goods; «курс», «онлайн-школ», «вебинар», «гайд», «подписчик» + «оплат» → digital; «абонемент», «подписк», «ежемесячн» → subscription; «ооо», «компани», «юрлиц», «b2b», «тендер» → b2b; «услуг» → services. Если ничего — модели сферы.
4. **Числа:** регулярки на русские и английские формы:
   - чек: `/(?:чек|средн\w* чек|стоимост\w*|от)\s*(?:около|примерно|~)?\s*([\d\s.,]+)\s*(к|тыс\w*|т\.р\.?|млн)?/`;
   - оборот: `/оборот\w*\s*(?:около|примерно|~)?\s*([\d\s.,]+)\s*(тыс\w*|млн|к)?/`, затем перевод в `revenueBand`;
   - поток: число рядом с «клиент», «заявок», «заказов», «стрижек», «записей», «в месяц», «в день» (× 26 для «в день»);
   - сотрудники: число рядом с «мастер», «сотрудник», «человек», «менеджер» → `size`.
   - `к`/`тыс` × 1000, `млн` × 1 000 000; диапазон «10–15» берёт среднее.
5. **Источники, приём заявок, оплата, боли:** по `keywords` из каталога.
6. **Название:** текст в кавычках «…» или "…" в первых 100 символах, иначе пусто.
7. `detected` — список полей, которые парсер заполнил. UI подсвечивает их.

Тест должен покрыть три примера из 01-product-ux.md, раздел 6: барбершоп → `beauty/barber`, `booking`, `check 1800`, `leads 400`, `src_maps`, `src_insta`, `intake dm`; кухни → `repair/furniture`, `check 250000`, `leads 12.5 → 13`, `src_avito`, `src_word`, `intake table`; курс → `education/online_school` или `digital/info` (оба допустимы), `digital`, `src_tg`, `payment card`.

## 9. layout — раскладка

- Колонки по этапам: `x = 80 + order × 280`. Ширина узла 216, высота 72 (компактный 56 при > 6 узлах в колонке).
- Внутри колонки узлы по порядку каталога, шаг по вертикали 96 (72 у компактных), колонка центрируется по вертикали относительно самой высокой колонки.
- `insight`: горизонтальная строка над схемой, `y = −140`, узлы центрируются над колонками `process` и `pay`.
- Петля возврата рисуется холстом под схемой, движок задаёт только `kind: 'loop'`.
- Ручные координаты узлов в `edited`-варианте `layout` не трогает, кроме команды «Выровнять».
- Для одинаковых блоков в разных вариантах координаты совпадают, когда это возможно (сначала раскладывается «Автопилот», затем остальные варианты берут координаты своих блоков оттуда и уплотняют колонки). Так морфинг между вариантами выглядит как «появились новые блоки», а не «всё перемешалось».
